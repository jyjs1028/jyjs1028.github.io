## Soft IRQ의 구조

커널 내부적으로 Soft IRQ는 `softirq_vec[]` 배열에 등록된 핸들러들로 구성되며, 총 10개의 타입이 존재한다.

```c
// kernel/softirq.c
static struct softirq_action softirq_vec[NR_SOFTIRQS];
```

| 번호 | 이름 | 역할 |
|---|---|---|
| 0 | HI_SOFTIRQ | 높은 우선순위 tasklet |
| 1 | TIMER_SOFTIRQ | 타이머 처리 |
| 2 | NET_TX_SOFTIRQ | 네트워크 송신 |
| 3 | NET_RX_SOFTIRQ | 네트워크 수신 |
| 4 | BLOCK_SOFTIRQ | 블록 I/O 완료 |
| 5 | IRQ_POLL_SOFTIRQ | I/O 폴링 |
| 6 | TASKLET_SOFTIRQ | 일반 tasklet |
| 7 | SCHED_SOFTIRQ | 스케줄러 부하 분산 |
| 8 | HRTIMER_SOFTIRQ | 고해상도 타이머 |
| 9 | RCU_SOFTIRQ | RCU 처리 |

## 실습 1: /proc/softirqs로 Soft IRQ 카운터 관찰

### 기본 확인

```bash
$ cat /proc/softirqs
```

```
                    CPU0       CPU1       CPU2       CPU3
          HI:          3          0          0          0
       TIMER:      45821      38476      41023      39982
      NET_TX:        124          0          0          0
      NET_RX:       8432       7821       6543       7102
       BLOCK:       2341       1823       1654       1987
    IRQ_POLL:          0          0          0          0
     TASKLET:        234        187        201        219
       SCHED:      98432      87654      91234      89543
     HRTIMER:          0          0          0          0
         RCU:      43211      39876      41234      40123
```

**관찰 포인트:**
- `TIMER`, `SCHED`, `RCU`가 압도적으로 많다 — 커널이 항상 처리하는 주기적 작업들
- `NET_TX`는 CPU0에만 쏠려 있다 — 송신은 주로 단일 CPU에서 처리
- `NET_RX`는 4개 코어에 분산 — 수신은 NAPI(New API)를 통해 균등 분배

---

### 네트워크 트래픽 발생 시 변화 관찰

터미널을 두 개 열어 동시에 실행한다.

**터미널 1 — 실시간 모니터링:**

```bash
$ watch -n 1 cat /proc/softirqs
```

**터미널 2 — 네트워크 부하 발생:**

```bash
# iperf3 서버 실행 (다른 머신에서)
$ iperf3 -s

# 클라이언트에서 트래픽 발생
$ iperf3 -c <192.168.0.15> -t 10
```

**부하 전:**

```
      NET_RX:       8432       7821       6543       7102
```

**부하 후 (10초 후):**

```
      NET_RX:      41238      39012      37654      38901
```

> NET_RX가 약 5배 증가했으며, 4개 코어에 고르게 분산된 것을 확인.

## 실습 2: ksoftirqd 스레드 확인

Soft IRQ 처리가 지연되거나 시스템이 바쁠 경우, 커널은 `ksoftirqd` 커널 스레드로 처리를 위임한다. CPU 개수만큼 생성된다.

```bash
$ ps aux | grep ksoftirqd
```

```
root         14  0.0  0.0      0     0 ?        S    08:21   0:00 [ksoftirqd/0]
root         22  0.0  0.0      0 0    ?        S    08:21   0:00 [ksoftirqd/1]
root         28  0.0  0.0      0     0 ?        S    08:21   0:00 [ksoftirqd/2]
root         34  0.0  0.0      0     0 ?        S    08:21   0:00 [ksoftirqd/3]
```

쿼드코어이므로 `ksoftirqd/0` ~ `ksoftirqd/3` 총 4개가 존재한다.

**고부하 상황에서 CPU 점유율 확인:**

```bash
$ iperf3 -c <192.168.0.42> -t 30 &
$ top -d 1
```

평소에는 CPU 0%인 ksoftirqd가 네트워크 부하 시 CPU를 점유하는 것을 확인할 수 있다.

> **왜 ksoftirqd가 존재하는가?**  
> `__do_softirq()`는 인터럽트 핸들러 리턴 직후 실행되는데, 처리가 너무 오래 걸리면 일반 프로세스가 CPU를 받지 못하는 starvation이 발생한다. ksoftirqd는 이를 방지하기 위해 나머지 작업을 일반 스케줄링 큐로 옮겨 처리한다.

## 실습 3: ftrace로 Soft IRQ 이벤트 추적

`ftrace`를 이용하면 Soft IRQ의 진입/종료 이벤트를 타임스탬프와 함께 추적할 수 있다.

### 사용 가능한 이벤트 확인

```bash
$ sudo ls /sys/kernel/debug/tracing/events/irq/ | grep soft
softirq_entry
softirq_exit
softirq_raise
```

### ftrace 설정 및 추적

```bash
# debugfs 마운트 확인
$ sudo mount -t debugfs nodev /sys/kernel/debug

# 이벤트 활성화
$ cd /sys/kernel/debug/tracing
$ sudo echo 0 > tracing_on
$ sudo echo > trace
$ sudo echo "softirq_entry softirq_exit softirq_raise" | sudo tee set_event
$ sudo echo 1 > tracing_on

# 10초 트래픽 발생
$ iperf3 -c <server_ip> -t 5 &
$ sleep 5

# 추적 종료 및 결과 확인
$ sudo echo 0 > tracing_on
$ sudo cat trace | head -50
```

### 출력 결과

```
# tracer: nop
#
# TASK-PID     CPU#  ||||    TIMESTAMP  FUNCTION
#    |           |   ||||       |            |
ksoftirqd/1-22  [001] d...    45.123401: softirq_raise: vec=3 [action=NET_RX]
      ksoftirqd/1-22  [001] d...    45.123412: softirq_entry: vec=3 [action=NET_RX]
      ksoftirqd/1-22  [001] d...    45.123498: softirq_exit: vec=3 [action=NET_RX]
      ksoftirqd/2-28  [002] d...    45.124001: softirq_raise: vec=3 [action=NET_RX]
      ksoftirqd/2-28  [002] d...    45.124015: softirq_entry: vec=3 [action=NET_RX]
      ksoftirqd/2-28  [002] d...    45.124089: softirq_exit: vec=3 [action=NET_RX]
      ksoftirqd/0-14  [000] d...    45.124321: softirq_raise: vec=7 [action=SCHED]
      ksoftirqd/0-14  [000] d...    45.124335: softirq_entry: vec=7 [action=SCHED]
      ksoftirqd/0-14  [000] d...    45.124402: softirq_exit: vec=7 [action=SCHED]
```

### 분석

| 항목 | 내용 |
|---|---|
| `softirq_raise` | Soft IRQ가 pending 상태로 등록됨 |
| `softirq_entry` | 실제 핸들러 실행 시작 |
| `softirq_exit` | 핸들러 실행 종료 |
| 처리 주체 | ksoftirqd/1, ksoftirqd/2 → 고부하로 인해 커널 스레드가 처리 |
| NET_RX 처리 시간 | entry → exit 기준 약 **86µs** (45.123412 → 45.123498) |

`raise` → `entry` 사이의 지연이 곧 Soft IRQ의 **latency**이며, 시스템 부하가 높을수록 이 값이 커진다.

---

### trace-cmd를 이용한 간편 추적

`ftrace`를 직접 다루는 대신 `trace-cmd` 래퍼를 쓰면 더 간편하다.

```bash
$ sudo apt install trace-cmd

# 5초 동안 softirq 이벤트 기록
$ sudo trace-cmd record -e "irq:softirq_entry" -e "irq:softirq_exit" sleep 5

# 결과 출력
$ sudo trace-cmd report | grep NET_RX | head -20
```

## 정리 및 결론

| 관찰 방법 | 알 수 있는 것 |
|---|---|
| `/proc/softirqs` | CPU별 누적 Soft IRQ 횟수, 타입별 처리 분포 |
| `ps aux \| grep ksoftirqd` | ksoftirqd 스레드 존재 확인, 고부하 시 CPU 점유 |
| `ftrace softirq_entry/exit` | 실제 처리 시간(latency), 처리 주체(CPU/스레드) |

**핵심 정리:**

1. Soft IRQ는 하드 인터럽트 처리 직후 실행되는 **지연 처리 메커니즘**이다.
2. `NET_RX`처럼 대량 처리가 필요한 서브시스템은 Soft IRQ로 구현되어 멀티코어에서 **병렬 처리**가 가능하다.
3. 시스템이 바쁠 경우 `ksoftirqd` 스레드가 처리를 대신 맡아 **일반 프로세스의 starvation을 방지**한다.
4. `ftrace`로 entry/exit 타임스탬프를 비교하면 Soft IRQ **latency를 정량적으로 측정**할 수 있다.
