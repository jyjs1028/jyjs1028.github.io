## 인터럽트 후반부 기법이란?
인터럽트 발생 시 인터럽트 핸들러는 빠르게 실행되어야 함. 그런데 인터럽트 핸들러에서 처리해야 할 일이 많으면? -> 이때 인터럽트 후반부 기법을 사용

**6.1.1 인터런트 후반부 기법을 적용하는 이유**
인터럽트 후반부: 인터럽트 핸들러에서 인터럽트를 바로 처리해야 할 코드를 실행한 다음에 인터럽트를 처리하는 시점을 의미

**remind: 인터럽트 처리과정**
1. 인터럽트 발생 -> 커널이 실행 중인 프로세스를 멈추고 인터럽트 벡터를 실행해서 인터럽트 핸들러를 실행
2. 인터럽트 핸들러는 짧고 빠르게 실행되어야 함
3. 인터럽트를 처리하는 구간이 인터럽트 컨텍스트이고 이를 in_interrupt()함수가 알려줌

**임베디드 리눅스 개발자: "인터럽트 핸들러에서 급하게 처리하지 않아도 되는 일은 조금 후에 해도 되지 않을까?"**
- 빨리 실행할 코드: 인터럽트 핸들러 및 인터럽트 컨텍스트
- 실시간으로 빨리 실행하지 않아도 되는 코드: 인터럽트 후반부 기법

**인터럽트 후반부 처리 기법 종류**
- IRQ 스레드
- Soft IRQ
- 태스크릿
- 워크큐

**6.1.2 인터런트 컨텍스트에서 많은 일을 하면 어떻게 될까?**
인터럽트 후반부 기법이 인터럽트 핸들러에서 짧고 간결하게 코드가 실행돼야 하기 때문에 도입됐는데 인터럽트 핸들러에서 실행 시간이 오래 걸리면 시스템은 어떻게 동작할까?
-> 대부분의 시스템이 오동작함

- I/O를 시작하는 코드
- 과도한 while 반복문
- 유저공간으로 uevent를 전달해서 인터럽트 발생을 알림
- 스케쥴링을 지원하는 커널 함수를 호출
위 같은 코드가 인터럽트 핸들러 혹은 핸들러 내부의 서브함수에서 동작하면 시스템이 아주 느려짐

**인터럽트 컨텍스트에서 발생한 커널 패닉**
커널에서는 인터럽트 컨텍스트에서 시간이 오래 걸리는 함수를 호출하면 커널 패닉을 유발하자는 제약을 두게 됨 -> 시스템이 오동작할 가능성이 높기 때문

13번~5번 흐름을 보면 인터럽트 컨텍스트에서 schedule()함수를 호출하여 스케쥴링을 시도하는데 커널이 이를 감지하고 커널 패닉을 유발함.

02번째 줄 로그를 자세히 보자. InputReader는 프로세스 이름, pid는 1039, 0x00010001은 프로세스의 thread_info구조체의 preempt_count 필드 값. 
여기서 두 가지 정보를 우리한테 말해주는데
1. 프로세스의 thread_info구조체의 preempt_count 필드 값이 0x00010001이니 현재 실행 중인 코드는 인터럽트 컨텍스트이다. 0x00010001을 HARDIRQ_MASK(0xF000)플래그와 AND비트 연산한 결과가 1이기 때문
2. 인터럽트 컨텍스트에서 schedule()함수를 호출했다. "아토믹 도중에 스케쥴링을 수행 중이다"를 알려줌. 이때 아토믹은 선점 스케쥴링이 되지 않는 실행 단위, 어떤 코드나 루틴이 실행 도중 스케쥴링을 수행하면 안되는 컨텍스트

정리하면 인터럽트가 발생 후 빨리 코드를 실행해야 하는데 스케쥴링을 지원하는 함수가 호출되면 프로세스가 휴면 상태에 진입할 수 있기 때문에 커널이 이를 감지하고 커널 패닉을 유발하는 것.

**6.1.3 TOP Half/Bottom Half란?**
인터럽트가 발생한 후 빨리 처리해야 하는 일은 Top Half -> 즉 인터럽트 핸들러가 하는 일
조금 있다가 처리해도 되는 일은 Bottom Half -> 인터럽트 처리를 프로세스 레벨에서 수행

**리눅스 커널에서 Bottom Half를 위해 어떤 기법을 지원할까?**
- IRQ 스레드
- Soft IRQ
- 태스크릿
- 워크큐

**인터럽트 컨텍스트와 프로세서 컨텍스트 레벨에서 코드를 실행할 때 차이점?**
인터럽트 컨텍스트 -> 호출 가능한 함수가 제한되어 있음(ex: 스케쥴링을 지원하는 뮤텍스나 schedule()같은 함수)
프로세서 컨텍스트 -> 스케쥴링을 포함한 모든 함수 사용 가능, 따라서 유연한 코드 설계 가능
**example**
인터럽트 발생 시 유저 공간에 알리고 싶은 경우가 존재.
안드로이드 디바이스의 경우 터치를 입력하면 발생하는 인터럽트를 uevent로 유저 공간에 알릴 수 있는데 시간이 오래 걸리는 동작임. 따라서 이 코드는 인터럽트 후반부에 처리하도록 드라이버 구조를 잡을 수가 있음.

**6.1.4 인터럽트 후반부 처리 기법의 종류**
4가지 기법의 특징이 다르기 때문에 상황에 따라 적용해야함!
**IRQ 스레드(threaded IRQ)**
: 인터럽트를 처리하는 전용 IRQ스레드에서 인터럽트 후속 처리를 수행. irq/24-rasp 란 rasp라는 24번 인터럽트 후반부를 IRQ스레드가 전담해서 처리한다는 것
**Soft IRQ**
: 인터럽트 핸들러에서 처리해야 할 일을 마무리 후 후반부 처리를 Soft IRQ 컨텍스트에서 실행. Soft IRQ 서비스 핸들러 실행 중 시간이 오래 걸리면 ksoftirqd 프로세스를 깨우고 Soft IRQ 서비스를 종료. ksoftirqd 프로세스에서 나머지 인터럽트 후반부를 처리하는 구조
**태스크릿**
: Soft IRQ를 동적으로 쓸 수 있는 인터페이스이자 자료구조임.
**워크큐**
: 인터럽트 핸들러가 실행될 때 워크를 워크큐에 큐잉하고 프로세스 레벨의 워커 스레드에서 인터럽트 후반부 처리함.

**6.1.5 어떤 인터럽트 후반부 처리 기법을 적용해야 할까?**
기준: 인터럽트 발생빈도, 인터럽트 후반부를 언제 처리하는지
책에서는 질답 형식으로 설명하던데 정리하면 1초에 인터럽트가 수백 번 발생하는 경우가 아니면 IRQ 스레드 방식을 적용해주면 되는데 대신 인터럽트 개수만큼 스레드를 생성하면 메모리를 더 사용하게 되긴 함. 하지만 현재 개발 중인 시스템 RAM용량이 8G 이상이면 큰 문제가 되진 않음.

But 인터럽트가 1초에 수십 수백 번 꼴로 자주 발생하는 경우는 Soft IRQ나 태스크릿을 적용하는게 좋음. IRQ스레드는 Real Time으로 구동되기 때문에 IRQ스레드가 실행되는 동안 다른 일반 프로세스들이 선점 스케쥴링이 불가능해짐. 따라서 IRQ 스레드 처리 함수의 실행 시간이 조금이라도 길어지면 다른 프로세스들이 실행을 못하고 대기하기 때문에 시스템 반응 속도가 느려질 수 있음.

비슷한 얘긴데 워크큐도 인터럽트 발생빈도가 높을 때 좋지 않음. 워크를 워크큐에 큐잉하고 워크를 깨우는 시간이 오래 걸리고 워커스레드는 일반 프로세스라 프로세스의 우선순위가 높지 않기 때문임.

결국 기법을 선택하는 것에 정답이 없기 때문에 인터럽트 처리가 최적화되도록 설계를 잘하려면 커널이 인터럽트를 처리하는 세부 동작 방식과 기법들의 세부 구현 방식을 잘 이해할 필요가 있음!!
